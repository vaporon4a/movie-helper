# Movie Helper

Telegram-бот для дружеского киноклуба: **мем дня, факт о кино, опросы по фильмам и еженедельный выбор новых функций**. Для ежедневных рубрик используется автоматический отбор Gemini с резервом Groq; киноопросы сохраняют анонимные интересы клуба без автоматических подборок.

Go 1.27.1, `go-telegram/bot`, SQLite с миграциями Goose, один процесс long polling. Docker Compose хранит данные в volume; домен и входящие порты не нужны.

## Запуск

1. Создайте бота через [BotFather](https://t.me/BotFather), добавьте в группу и разрешите отправлять текст, фотографии и опросы. Административные права и чтение всей переписки боту не нужны. Команды адресуйте `/help@имя_бота`, особенно при включённом Privacy Mode. `/help` показывает основные команды с кнопками навигации. Все участники клуба имеют одинаковые права на команды, настройки и общие записи.
2. Подготовьте конфигурацию:

   ```sh
   cp .env.example .env
   chmod 600 .env
   ```

   В `.env` заполните `BOT_TOKEN`, `ALLOWED_CHAT_IDS` (отрицательные ID групп через запятую), `TMDB_API_TOKEN` для киноопросов и хотя бы один AI-ключ для мемов и фактов. Используется TMDB API Read Access Token (Bearer), а не короткий API key. Реальные ключи не добавляйте в Git. Для первого определения ID задайте `ALLOWED_CHAT_IDS=bootstrap` (ни одна группа пока не разрешена), запустите бота и отправьте `/id@имя_бота` в нужной группе: эта команда работает вне списка. Затем обновите `.env` и пересоздайте контейнер.
3. Запустите:

   ```sh
   docker compose up -d --build
   docker compose logs --tail=100 -f bot
   ```

4. Участник группы явно включает рубрики:

   ```text
   /timezone@имя_бота Europe/Moscow
   /schedule@имя_бота meme 09:00
   /schedule@имя_бота fact 12:00
   /settings@имя_бота
   ```

Рассылка изначально выключена. Время относится к часовому поясу чата. Если сегодняшнее время уже наступило, первое сообщение будет завтра. `/pause meme` и `/pause fact` выключают соответствующую рубрику. Изменения `.env` применяются через `docker compose up -d --force-recreate`, а не `restart`.

Один токен обслуживает один процесс. Активный webhook препятствует запуску; приложение не удаляет его автоматически. Второй процесс с той же БД блокируется файловой блокировкой. SQLite рассчитана на локальный Docker volume одного сервера.

## Помощь и настройки

В `/help` и меню Telegram пять основных команд: `/movie_watched`, `/movie_profile`, `/idea`, `/my_ideas`, `/settings`.

`/settings` открывает разделы: просмотры и опросы, мемы и факты, встречи, идеи, дополнительные инструменты. На главном экране виден часовой пояс; модерация и диагностика вынесены в «Дополнительно». Переходы обновляют одно сообщение и не меняют настройки. Внизу интерактивных панелей есть «Закрыть»: она удаляет только сообщение, сохраняя просмотры и ответы; если Telegram запрещает удаление старого сообщения, убирает кнопки. Закрытые карточки просмотров не обновляются в фоне. В «Мемы и факты» выберите рубрику: включение, подтверждённая пауза, время и пример доступны кнопками. Для времени бот создаёт адресный запрос на 10 минут: ответьте на него в формате HH:MM. Смена времени не включает выключенную рубрику. Если другой участник изменил настройки, устаревшее действие не применяется. Остальные расписания пока задаются командами по примерам внутри разделов.

Пример из меню берётся только из готового запаса. Если он пуст, запускается фоновая подготовка — нажмите кнопку позже. Предпросмотр не меняет расписание, между показами одной рубрики в чате — 30 секунд. Неопределённую доставку бот автоматически не повторяет: сначала проверьте чат.

Старые команды продолжают работать: `/movie_settings`, `/club_settings`, `/idea_settings` и `/help_manage` (прежняя `/help_admin`) открывают свои разделы. `/movie_taste` остаётся синонимом `/movie_profile`. В личке доступна общая справка; настройки открываются в подключённой группе.

При запуске бот обновляет меню Telegram до пяти основных команд для языка по умолчанию и русского. Сбой обновления меню не останавливает бота.

## Киноопросы и профиль клуба

Кино для встречи выбирают участники. Бот проводит анонимные опросы о жанрах и знакомых фильмах, сохраняет результаты и не присылает рекомендации, постеры или отдельные итоги после закрытия.

```text
/genre_poll@имя_бота 5m
/reference_poll@имя_бота 5m
/movie_schedule@имя_бота genre wed 09:00
/movie_schedule@имя_бота reference wed 12:00
/movie_settings@имя_бота
/movie_pause@имя_бота genre wed
/movie_profile@имя_бота
```

Команды доступны каждому участнику разрешённого чата. Без длительности ручной опрос открыт 24 часа; поддерживается диапазон 5m–24h. Плановый опрос открыт 24 часа от фактической отправки. Разные опросы могут идти одновременно. Пропущенные более чем на 30 минут слоты не догоняются.

Снимок каждого нового вопроса включает точную формулировку, варианты, шкалу и версию. Финал сохраняет все счётчики, общее число ответивших и происхождение ответа Telegram. Персональные голоса не собираются. Повтор одного update не прибавляет голоса. Отсутствующий или противоречивый финал не считается нулевым результатом.

В reference-опросе восемь фильмов из подготовленного каталога и вариант «Не знаком(а) / не могу выбрать». Ротация учитывает недавние показы; для этих опросов не нужны AI или доступность TMDB. Исторические вопросы о подборках сохраняются отдельно как прежний интерес: не восстанавливаем отсутствующие тексты и общее число ответивших догадками.

`/movie_profile` открывает карточку с историей просмотров, общими впечатлениями, аспектами и интересами. Кнопки показывают сохранённые вопросы и полные распределения ответов. `/movie_taste` — алиас. `/movie_personalization` и `/movie_taste_reset` объясняют переход и не меняют журнал.

Карточка просмотра компактная: «Впечатления», «Подробнее» и «Другие действия». Подробности показывают подготовку вопросов, фактически принятый план, прогресс и очередь. Ближайшее окно — время обсуждений клуба, а не обещание вопросов именно об этом фильме. Фоновые изменения обновляют открытую страницу, сохраняя навигацию; закрытые карточки не появляются заново.


Добавить просмотр может любой участник:

```text
/movie_watched https://www.themoviedb.org/movie/603
/movie_watched Матрица | 2026-10-16
/movie_watched Матрица | 2020
/movie_watched Матрица | unknown
/movie_auto_review off
/movie_watch_date 1 2026-10-17
```

Ссылка сразу подтверждает фильм; название предлагает до пяти кандидатов, один выбор сохраняет просмотр. По умолчанию дата — сегодня в часовом поясе чата. Будущие даты запрещены. Недоступность TMDB оставляет заявку на 24 часа с фоновыми повторами и одной обновляемой карточкой. Неизвестная/неточная или старая дата означает историю без автоматической серии. Повтор фильма в другую дату — отдельный просмотр; одинаковые фильм/точная дата/чат не дублируются. Исправление даты вручную сохраняет аудит и ответы, но останавливает продолжение серии. «Остановить вопросы…» требует отдельного подтверждения и оставляет фильм в истории. Отмена просмотра кнопкой отключена, в том числе в старых карточках; ошибочную запись исправляем вручную при обслуживании бота. «Исправить» показывает инструкцию в той же карточке, не отправляя новое сообщение в чат. Чужую запись своего чата могут исправить все участники.

Для свежего просмотра автоматически создаётся программа: общее впечатление, темп, вовлечённость, герои и визуальная сторона. В каждом вопросе есть «Не смотрел(а)» и «Не могу оценить», они не считаются содержательными оценками. Нейтральные и отрицательные ответы считаются. Для покрытия каждой темы нужно минимум три содержательных ответа в одном завершённом вопросе; повторы не суммируются в выдуманное число людей.

Четыре включённых недельных слота распределяются как два обычных и два исследовательских. Защищены как минимум один genre и один reference. В исследовательском слоте до двух вопросов, максимум шесть poll-сообщений в неделю при четырёх слотах. Без подходящей серии исследовательский слот становится обычным. При одном слоте исследование ждёт настройки. Роли фиксируются на неделю; добавленный в середине недели слот остаётся обычным до следующей недели. Одна серия на чат идёт первой по очереди, обычные опросы не блокируются. Пропуски не создают пачку догоняющих публикаций.

Серия обычно состоит из пяти вопросов; предел — семь отправленных/неопределённо доставленных, максимум два на одну тему. При добавлении в автоматическую очередь попадают просмотры с точной датой моложе 14 календарных дней. Ожидание очереди не ограничено: 28 суток обсуждения начинаются с первой подтверждённой публикации вопроса. Резервирование слота, ошибка отправки и неопределённая доставка не запускают отсчёт; следующие вопросы и перезапуски не продлевают срок. Если два закрытых блока подряд не дали содержательных оценок, закончились повторы/бюджет или срок, серия завершается с явной неполнотой. Остановленные серии не перезапускаются автоматически. При переходе на новый отсчёт в очередь возвращаются только серии, закрытые прежним сроком до первой подтверждённой публикации, если просмотр активен и автоматическое обсуждение включено. `/movie_auto_review off` останавливает дальнейшие вопросы и автоматическую постановку новых просмотров; включение не создаёт опросы для старой истории. Расписание самостоятельно не включается.

После подтверждённого финала результат и задача удаления записываются одной транзакцией. Отдельный worker удаляет только собственные новые киноопросы. Повторы удаления ограничены 47 часами от отправки; запрет Telegram и просрочка видны в `/movie_settings`, ответы остаются в профиле. Старые сообщения и другие рубрики не удаляются. Если бот был выключен слишком долго, удаление может не состояться.

Профиль разделяет интерес до просмотра и впечатления после. Общая оценка показывается с настоящим знаменателем; число ответов разных вопросов не выдаётся за число уникальных участников. Сводка аспектов появляется от трёх разных фильмов, каждому фильму даётся равный вес. Отменённые просмотры исключаются из сводки. Переписка и личные голоса не собираются; шаблонный режим работает без AI. Метаданные TMDB дополняются отдельно в фоне, их недоступность не блокирует шаблонные вопросы.

Адресные опросы можно включить отдельно: `FILM_RESEARCH_MODE=shadow` для подготовки без публикации или `on` для новых просмотров. По умолчанию `off`. `FILM_RESEARCH_CHAT_IDS` ограничивает пилот выбранными разрешёнными чатами. Бот собирает контекст TMDB/Wikipedia, готовит и проверяет четыре вопроса в фоне. Если набор не готов к первому слоту, используется вся прежняя шаблонная серия; начатые опросы не меняются. В профиле появился отдельный раздел «Особенности фильмов» с сопоставимыми агрегатами. [Контракт, эксплуатация и приёмка](internal/filmresearch/README.md).

Для анализа оператор может выгрузить агрегаты одного чата из read-only SQLite-снимка (JSON содержит просмотры, метаданные, сессии, вопросы, финалы, исправления и cleanup; CSV — ответы по вариантам):

```sh
python3 scripts/export_club_profile.py --db /path/to/movie-helper.db --chat=-1003352894979 --output club-profile.json
python3 scripts/export_club_profile.py --db /path/to/movie-helper.db --chat=-1003352894979 --format csv --output club-votes.csv
```

Экспорт не отправляется в Telegram, существующий файл не перезаписывается. Неизвестные значения остаются пустыми/null. Массовый импорт и AI-уточнения — следующие этапы.

Расписания переносятся с сохранением включения, дней, времени и часового пояса. Уже открытые старые опросы завершаются без подборки. Старые кнопки «Ещё 10» не отправляют альбомы. Старый движок рекомендаций удалён; таблицы и миграции сохраняются для переноса истории. При подтверждённой ошибке доступна `/movie_resolve ID retry`; неопределённая отправка не повторяется автоматически. `/movie_resolve ID cancel` снимает ещё не отправленный либо проблемный раунд. Статус `result_missing` означает отсутствие подтверждённых итогов, а не отсутствие голосов.

Фоновые задания просмотров и удаления опросов выбираются отдельно для каждого разрешённого активного чата. Если Telegram отклонил первую карточку просмотра с `429`, бот сохраняет `Retry-After` и повторяет отправку в фоне, в том числе после перезапуска. Неопределённая доставка не повторяется автоматически.

## Голосование за функции

Любой участник разрешённой группы может предложить функцию прямой командой `/idea Текст` или вызвать `/idea` и ответить на запрос бота. Исходный текст должен содержать 20–1500 символов; один пользователь может добавить не более 20 идей за скользящие семь дней. `/my_ideas` показывает собственные активные предложения, `/idea_cancel ID` отзывает предложение, если оно ещё не попало в открытый раунд.

Любой участник включает один еженедельный слот и при необходимости запускает короткую проверку:

```text
/idea_schedule@имя_бота sun 18:00
/idea_round@имя_бота 5m
/idea_settings@имя_бота
/idea_pause@имя_бота
```

Все идеи в состоянии `active` участвуют в каждом основном раунде без ограничения количества и числа предыдущих участий. При 2–12 вариантах бот публикует нативный анонимный Telegram Poll: короткие AI-названия служат вариантами, голос можно изменить, а кнопка `📋 Полные описания` открывает исходные тексты в личном чате. Telegram допускает не более 12 вариантов. При одной или 13+ идеях бот автоматически использует приватный бюллетень с пагинацией и одним изменяемым голосом, поэтому ни одна идея не исключается.

Deep link содержит длинный случайный токен раунда и служит ключом к полным описаниям, а в приватном режиме — также к голосованию. Бот не требует административных прав и не проверяет членство в исходной группе; пересланная ссылка позволит другому пользователю открыть идеи и, для приватного бюллетеня, проголосовать.

Через 24 часа единственный победитель автоматически переходит в бэклог и исключается из дальнейших голосований. Проигравшие остаются активными. При равенстве голосов бот запускает 12-часовой второй тур между лидерами; повторная ничья завершается без победителя и без бесконечной цепочки новых туров. При отсутствии голосов состояния идей не меняются. `/idea_backlog` показывает победителей. Любой участник управляет жизненным циклом командами `/idea_remove ID`, `/idea_done ID` и `/idea_restore ID`.

Gemini с резервом Groq используется только один раз для короткого названия новой идеи. Название готовится фоновым заданием сразу после сохранения исходного текста; открытие голосования не ждёт AI. Если заголовок ещё не готов, бот использует локальный короткий вариант и всё равно открывает раунд. AI не отбирает, не ранжирует и не объединяет предложения. Нативный Poll анонимен: бот получает только итоговые счётчики. В приватном режиме Telegram ID голоса хранится до подсчёта результата, не показывается участникам и не записывается в логи; после подсчёта остаются только итоговые числа.

## Откуда берутся материалы

**По умолчанию материалы отбирает и одобряет AI; участие человека не требуется.** Предложения участников сохраняются, но в автоматическом режиме не публикуются. Источники:

- Мемы: [Meme API](https://github.com/D3vd/Meme_Api), по умолчанию `RUSSIANMemeSub,Pikabu,expectedrussians`. Бот запрашивает до 50 записей на каждый subreddit; провайдер может вернуть меньше. Действуют фильтры NSFW/спойлеров, русскоязычного заголовка и формата JPG/PNG с `i.redd.it`. Для AI используется самый крупный безопасный `preview.redd.it`, а в Telegram публикуется оригинал. При отсутствии preview разрешён оригинал до 8 MiB; перед AI изображение проверяется по размерности и уменьшается до 1280 px (JPEG quality 85, маленький PNG сохраняется, если он компактнее). Gemini просматривает до четырёх картинок за запрос (максимум две порции), резервный Groq — до двух за одну порцию. Модель сначала описывает видимое и развязку, затем оценивает юмор, понятность и оригинальность по шкале 1–5. Одиночная опечатка или подпись без дополнительной находки могут попасть только в резерв. Код разрешает публикацию только при юморе и понятности не ниже 4; при обеих оценках не ниже 3 материал остаётся в резерве, иначе отклоняется. Оригинальность влияет на порядок: хороший простой каламбур допустим. Длина, научная тема и водяные знаки сами по себе не запрещены. Уточнённый промпт учитывает редакторские оценки участника киноклуба; это не автоматическое обучение по реакциям всех участников. В готовый запас идут только publish, резерв не используется при пустом запасе. Для каждого решения сохраняются оценки и наблюдения: publish — в source_evidence материала, reserve/reject — в rejection-cache на 24 часа. Для мемов отдельно задаётся `GEMINI_MEME_MODEL` (по умолчанию `gemini-3.5-flash-lite`); факты, названия идей и напоминания сохраняют `GEMINI_MODEL`. Квота Gemini остаётся общей. Невалидные индексы/оценки отклоняют ответ целиком; пустое или чрезмерно длинное объяснение отклоняет только соответствующую картинку без отравления source-cache. Политика meme-v4; прежние известные неотправленные AI-мемы выводятся из буфера при обновлении. Ручные предложения и sending/unknown/sent сохраняются. Содержательные и постоянные технические отказы кэшируются в SQLite на 24 часа; история публикаций отдельная для каждого чата. `MEME_SUBREDDITS` позволяет задать до пяти источников через запятую.
- Факты: исходные русские эпизоды из разделов создания фильмов в Wikipedia. TMDB даёт разнообразный каталог пяти эпох, русскоязычных фильмов и недельных трендов. Wikidata подтверждает TMDB ID, IMDb ID при наличии, название и год; QID самой статьи проверяется повторно. Неоднозначные сопоставления пропускаются.

AI оценивает понятность и интерес каждого фрагмента по шкале 1–5: для публикации нужны обе оценки не ниже 4. Он возвращает только номера и оценки, **не переводит и не переписывает текст**. Короткая законченная история допустима; обрывки, сюжет, перечисления имён и неясные причинные связи отклоняются. Публикуются локально сохранённые исходные слова, название фильма, ссылка на конкретную редакцию и CC BY-SA 4.0. Evidence содержит снимок эпизода с ID фильма, QID, ревизией, разделом и ключом; политика — `fact-extractive-ru-v1`. Это предотвращает добавление моделью деталей, но не доказывает достоверность самой статьи.

Каталог кешируется на сутки, при сбое допускается сохранённая версия не старше семи дней. Источники с эпизодами кешируются на 14 дней, отсутствие материала — на сутки. За задачу проверяются до четырёх фильмов, в AI идут до трёх фрагментов каждого. Прогресс обхода хранится в SQLite; повторное обращение к AI после временного сбоя использует тот же подготовленный batch. Один и тот же текст не повторяется после смены ревизии. Для каждого чата фильм исключается на 30 дней после подготовки истории; готовый факт того же фильма блокирует новый до использования. Нужен `TMDB_API_TOKEN`. `FACT_WIKI_TITLES` сохранён для совместимости старого адаптера и больше не управляет production-поиском.

При обновлении старые AI-факты, которые точно ещё не отправлены, исключаются из запаса. Их `ready/retry` доставки возвращаются к ожиданию нового материала. Ручные предложения, история, квоты, `sending/unknown` не изменяются. Новые факты появляются в `/preview fact` после первой успешной фоновой подготовки, в чате — по следующему расписанию либо в ещё действующем окне текущего слота. Просроченные дни автоматически не догоняются.

Переписка участников, их имена и ручная очередь провайдерам AI не передаются: только общедоступные картинки, заголовки и фрагменты статей.

Факты, мемы и короткие названия идей готовятся заранее фоновым координатором и сохраняются в SQLite. Для каждой включённой ежедневной рубрики целевой запас — пять материалов, нижний порог — три; мем старше семи дней в запасе больше не используется. Публикация по расписанию и `/preview` читают готовый результат без ожидания внешнего AI. Если запас пуст, бот ставит срочное фоновое задание и продолжает проверять БД до конца допустимого окна публикации. Задания переживают перезапуск, имеют lease от параллельного выполнения и повторяются через 5, 15, 30, 60 и 120 минут. `/settings` показывает текущий запас и последнюю безопасную причину ожидания, а `/refill fact|meme|titles` позволяет любому участнику запросить внеочередное пополнение.

Без обоих ключей (`GEMINI_API_KEY` и `GROQ_API_KEY`) фоновые задания не получают новых материалов; уже готовый запас и ручная очередь при `/moderation on` остаются доступны. Временные ответы Gemini (`408`, `429`, `500`, `502`, `503`, `504`) и `429` от Groq несут безопасную рекомендацию по времени повтора. Пауза до 10 секунд выполняется внутри клиента один раз. Более длинный `Retry-After` откладывает фоновое задание, не блокируя расписания; задержка ограничена пятью минутами. Такой ответ Gemini сначала повторяет основной провайдер и не переключает запрос на Groq раньше рекомендованного времени. При отсутствии `Retry-After` Groq используется пауза в одну минуту. Постоянные ошибки сразу переходят в обычный fallback. Валидный полный отказ Gemini не обходится резервной моделью. Непроверенный контент не публикуется.

`AI_RESULT_MODE=warmup` сохраняет синхронное получение мемов как временную страховку, пока фоновые пулы наполняются. Факты всегда берутся только из готового запаса. После проверки запаса в production значение `background` запрещает пользовательским командам и планировщику обращаться к AI напрямую. Переключение не меняет сохранённые расписания и материалы.

### Реакции на мемы и факты

Бот сохраняет обычные, кастомные и платные реакции на **новые подтверждённые мемы и факты** в разрешённых группах. Для получения этих событий Telegram требует статус администратора бота; события `message_reaction` и `message_reaction_count` включены явно. Отдельных команд участникам не нужно. Реакции на чужие сообщения, меню, киноопросы и анонсы не собираются.

В SQLite сохраняются снимок материала (текст, источник, ссылка на картинку, evidence/оценки, провайдер, модель и версия политики), время публикации, текущие счётчики и история изменений. Имена и Telegram ID реагировавших участников не сохраняются. `/preview` отмечается отдельно от публикаций по расписанию. Для ранее подготовленного материала неизвестная модель остаётся пустой: текущая настройка модели не подставляется задним числом.

Замена/удаление реакции изменяет счётчик; повтор одного `update_id` не учитывается дважды, в том числе после перезапуска. Анонимное событие содержит полный снимок и **заменяет**, а не увеличивает счётчики. Запоздавшие снимки сохраняются в истории с `applied=false` и не откатывают новые значения. При отрицательной дельте без известного добавления либо смене режима счётчиков материал помечается `partial`; отрицательное значение сохраняется как диагностический сигнал, а не выдаётся за точное число реакций.

Это только накопление данных: эмодзи не получают положительных/отрицательных весов, промпты и фильтры автоматически не меняются, AI-запросы не выполняются. Отсутствие реакций не означает плохой материал, сумма разных эмодзи не равна числу участников. Старые реакции не восстанавливаются. События могут задерживаться; длительный простой или ошибка записи могут привести к пропускам, которые не всегда обнаружимы. Выгрузка поэтому явно помечена `observed_updates_only`. Ошибка регистрации статистики не повторяет уже подтверждённую отправку поста; причина видна в безопасном предупреждении лога.

Для будущего анализа есть read-only JSONL-выгрузка из рабочей SQLite или её согласованной резервной копии:

```bash
python3 deploy/export_feedback.py --db /path/movie-helper.db --chat-id -1003352894979 --kind meme > meme-feedback.jsonl
python3 deploy/export_feedback.py --db /path/movie-helper.db --publication all --since 2026-10-10 > all-feedback.jsonl
```

По умолчанию экспортируются только публикации по расписанию, включая посты **без реакций**. Каждая строка содержит `post`, `reactions`, `events`, `schema_version` и обозначение полноты наблюдений; `--publication preview` позволяет отдельно проверить предпросмотры. Выгрузка не мигрирует и не создаёт БД, читает посты/счётчики/события в одном снимке. Для копирования работающей WAL-БД используйте штатный backup, а не один файл `.db` без WAL.

### Режим публикации и быстрая проверка

Настройка отдельная для каждого чата и хранится в SQLite:

- `/moderation off` — по умолчанию: AI выбирает материалы, они публикуются по расписанию без ручного одобрения. Сохранённые результаты AI после отмены или явного `/resolve ID requeue` также могут использоваться; ручные предложения не публикуются.
- `/moderation on` — публикуются только материалы после `/approve ID` участником клуба. Если одобренных нет, AI подбирает материал в очередной слот и сохраняет его в `/queue` со статусом `pending`; публикация возможна в следующий слот после одобрения. В этом режиме можно публиковать и предложения участников.
- `/settings` показывает режим и расписание. Переключение режима сохраняет материалы и отменяет ожидающие доставки; сетевой запрос, уже отправленный в Telegram, может завершиться. Расписание при переключении не включается автоматически.

Для немедленной проверки любой участник отправляет в разрешённую группу:

```text
/preview@имя_бота meme
/preview@имя_бота fact
```

Бот пришлёт готовый материал из запаса с пометкой «Предпросмотр». Команда не включает расписание и не отмечает материал как опубликованный, поэтому он может встретиться позже в ежедневной рубрике. При пустом запасе в режиме `background` бот запустит фоновое пополнение и предложит повторить предпросмотр позже; команда не ждёт внешний AI.

Существующие чаты после обновления тоже получают `/moderation off`; прежние ручные предложения остаются в базе. Для их публикации включите `/moderation on`.

### Gemini и Groq

Ключ создаётся в [Google AI Studio](https://aistudio.google.com/apikey). Модель задаётся `GEMINI_MODEL`, по умолчанию `gemini-3.8-flash`; используется REST `generateContent` со структурированным JSON-ответом. Выбранная замена должна поддерживать изображения и JSON Schema.

`GEMINI_DAILY_REQUEST_LIMIT=20` — общий предел **попыток** обращения ко всем чатам за UTC-сутки. Счётчик хранится в SQLite и переживает перезапуск; ошибки тоже расходуют попытку. `0` блокирует вызовы модели. Отказы, исправления ответа и повторы расходуют дополнительные попытки; чтение готового запаса через расписание или `/preview` квоту не расходует. Это ограничение числа запросов, а не бюджета в деньгах: проверьте [тариф модели](https://ai.google.dev/gemini-api/docs/pricing), [квоты проекта](https://ai.google.dev/gemini-api/docs/rate-limits), [доступность региона](https://ai.google.dev/gemini-api/docs/available-regions) и [условия обработки данных](https://ai.google.dev/gemini-api/terms).

Встроенный Google Search grounding не используется. Независимые источники позволяют сохранять очередь и публиковать её по расписанию без привязки к поисковому ответу конкретному пользователю.

Groq — отдельный резервный провайдер: `GROQ_API_KEY`, модель `GROQ_MODEL=qwen/qwen3.8-27b`, сохраняемый предел `GROQ_DAILY_REQUEST_LIMIT=20` попыток за UTC-сутки. Его счётчик независим от Gemini; `0` отключает вызовы Groq. Если задан только Groq-ключ, бот работает через него. При двух ключах порядок Gemini → Groq. Для факта provider выполняет выбор с возможным исправлением структуры, а затем обязательный редакторский проход; для мемов Groq проверяет три кандидата. Каждая HTTP-попытка, включая один retry временной ошибки Gemini, отдельно расходует дневной лимит. Один HTTP-запрос к Gemini может ждать до 60 секунд, к Groq — до 25 секунд. На весь provider attempt у Gemini выделено 150 секунд, у Groq — 60 секунд, а на одно фоновое получение материала — 4 минуты. Ошибки HTTP, тайм-аут и непрошедший проверку ответ позволяют перейти к резерву. В логах сохраняются безопасные коды ошибок HTTP и проверки ответа; ключи и полные ответы с ошибками не попадают в логи.

Для Groq используются строгая JSON Schema и `reasoning_effort=none`. Текстовые задачи сохраняют свой лимит ответа; для более подробных оценок мемов выделяется не менее 2048 выходных токенов. Один vision-запрос содержит до двух картинок. Фактические квоты аккаунта проверяются отдельно: уменьшение пакета не гарантирует отсутствие 429. Сжатие уменьшает байты запроса, но не фиксированную стоимость изображения в токенах Groq. После `429` фоновое задание повторяется позже. Для фактов проверяется дословная непрерывная цитата из источника: целевая длина 20–50 слов, допустимо до 80 слов и 800 символов (минимум 20 символов); итоговый факт содержит 30–110 слов, обычно 65–100, и проходит обязательную редактуру. При нарушении структуры бот один раз просит AI исправить черновик, учитывая общий дневной лимит; ограничения не ослабляются при переключении. Модель Groq находится в Preview, доступность и квоты могут меняться: [vision](https://console.groq.com/docs/vision), [лимиты](https://console.groq.com/docs/rate-limits), [данные](https://console.groq.com/docs/your-data).

## Очередь и права

- Участник отвечает `/suggest_meme@имя_бота` на одну фотографию, не альбом. Бот сохраняет Telegram `file_id`, без скачивания файла. С Privacy Mode надёжнее адресовать команду явно.
- `/suggest_fact Текст факта | https://источник` добавляет предложение с текстом до 1500 символов.
- Участник открывает `/queue`, затем `/review ID` и нажимает «Одобрить» или «Убрать». Есть команды `/approve ID` и `/reject ID`. Для следующей страницы: `/queue последний_ID`.
- Ручное предложение публикуется только после одобрения. Автоматически отобранные внешние материалы публикуются без отдельного одобрения.
- Изменять расписание, очередь и общие записи может любой участник разрешённой группы. Роль администратора и авторство записи не дают привилегий. Анонимные команды от имени чата не принимаются; данные других чатов недоступны.
- Материалы, история повторов и настройки изолированы по `chat_id`; ID материала чужого чата не даёт к нему доступ. Эти данные доступны участникам своей группы и оператору сервера, а не являются зашифрованным хранилищем.

## Доставка и восстановление

Проверка расписания идёт каждые 15 секунд. Один слот каждой рубрики на локальную дату; окно подбора и отправки — до 6 часов после назначенного времени, но не позже конца местного дня. После простоя публикация догоняется только внутри этого окна. Число попыток и время следующего подбора хранятся в SQLite и сохраняются при перезапуске; прерванный подбор повторяется не раньше чем через 5 минут после запуска. При смене режима, времени или часового пояса ожидающие доставки отменяются, материал возвращается в очередь. Уже отправляемый сетевой запрос может завершиться.

После подтверждённого Telegram `429` учитывается `retry_after` в пределах окна. При потере доступа к чату рассылка выключается: восстановите права, выполните `/resume` и снова `/schedule`. Преобразование группы в supergroup требует нового `ALLOWED_CHAT_IDS` и настройки в новом чате; старая история сохраняется под старым ID и автоматически не переносится.

Telegram и SQLite не имеют общей транзакции. После таймаута или падения между отправкой и записью результата доставка становится `unknown` и автоматически не повторяется. `/settings` показывает ожидающие повторы, число попыток, время следующего подбора, а также последние пропущенные, неопределённые и ошибочные доставки. Проверьте чат и выполните `/resolve ID sent`, если пост появился, либо `/resolve ID requeue`, чтобы вернуть материал в очередь **следующего доступного дня**. Во втором случае возможен повтор. Материал публикуется в подходящем режиме: ручное предложение требует `/moderation on`, результат Gemini — его AI-одобрения в автоматическом режиме или одобрения участника клуба в ручном. Строгая exactly-once доставка не обещается.

Логи содержат тип события и технические ID, без токенов, текста переписки и полных ответов внешних API. Для публичных мемов дополнительно записываются размеры копий, ссылка-идентификатор источника и причина, решение publish/reserve/reject, оценки юмора, понятности и оригинальности. Короткое наблюдение и объяснение шутки сохраняются в аудитных полях SQLite, а не в общий лог. Недоступность источника видна в логах. Ошибочные материалы не повторяются бесконечно.

## Обновление, CI и резервные копии

Workflow проверяет форматирование, `go vet`, тесты с race, `golangci-lint`, Compose и Docker build. Локально линтер запускается командой `golangci-lint run ./...`; для Go 1.27 нужна версия не ниже 2.14.0, в CI зафиксирована 2.14.0. После успешных проверок push в `main` или тега `v*` публикует `ghcr.io/vaporon4a/movie-helper:sha-<полный commit SHA>`. Push в `main` затем автоматически обновляет сервер опубликованным образом этого коммита. PR образ не публикует, теги сервер не обновляют. Публикация требует разрешения GitHub Packages для репозитория. Для приватного GHCR серверу нужен отдельный вход с правом чтения пакета.

Для готового образа задайте `BOT_IMAGE` в `.env`, затем:

```sh
docker compose pull bot
docker compose up -d --no-build
```

Перед обновлениями сохраняйте volume с остановленным ботом. Пример согласованной копии (архив включает БД и возможные WAL-файлы):

```sh
docker compose stop bot
mkdir -p backups
bot_volume=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps -aq bot)")
bot_backup="movie-helper-$(date -u +%Y%m%dT%H%M%SZ).tgz"
docker run --rm --mount "source=$bot_volume,target=/data,readonly" \
  --mount "type=bind,src=$PWD/backups,target=/backup" alpine:3.23 \
  tar czf "/backup/$bot_backup" -C /data .
docker compose start bot
```

Скопируйте архив во внешнее место; `.env` храните отдельно. Для восстановления остановите бота, распакуйте архив в **новый пустой volume**, сохраните владельца `65532:65532` и подключите его вместо `bot-data`. Проверьте `/settings` и `/queue`, прежде чем включать рассылку. Не копируйте отдельный файл работающей SQLite и не используйте `docker compose down -v`: он удаляет данные. Откат приложения с несовместимой схемой требует совместимой резервной копии; автоматического Down при запуске нет.

### Ежедневные копии в Backblaze B2

`deploy/scheduled_backup.py` останавливает работающего бота, архивирует `/data`,
запускает тот же контейнер и затем проверяет SQLite, загружает архив через
`rclone crypt`, скачивает его обратно и сверяет SHA-256. Общая блокировка с деплоем
исключает обновление во время снимка. При ошибке архивации выполняется попытка
запуска бота; SIGKILL или отключение сервера требуют отдельной проверки состояния.
Если бот уже остановлен, скрипт завершится с ошибкой, не включая его самостоятельно.

Конфигурация для production: закрытый bucket `movie-helper-backups-20260923`,
подкаталог `archives`, конфиг `/opt/movie-helper/secrets/rclone.conf` (0600),
пользователь `movie-helper-deploy`. На сервере нужны Python 3, Docker и rclone.
Скопируйте `remote.py`, `configure_backup.py` и `scheduled_backup.py` из `deploy/`
в `/opt/movie-helper/backup-tools/`; эти инструменты устанавливаются отдельно от
релизов и не обновляются автоматически вместе с ботом.

Для ввода ключа запустите **в собственном интерактивном SSH-терминале**:

```sh
sudo -u movie-helper-deploy python3 /opt/movie-helper/backup-tools/configure_backup.py
```

Скрипт запросит keyID, applicationKey и пароль шифрования (от 24 символов) с
повтором. Ввод скрыт, существующий конфиг не перезаписывается. Ключ B2 должен
иметь доступ к этому bucket на просмотр, чтение, запись и удаление файлов.
Пароль шифрования заранее сохраните в менеджере паролей вне сервера: без него
восстановить архивы невозможно. Обфускация пароля в rclone.conf обратима, поэтому
весь конфиг является секретом; не выводите его в логи и не добавляйте в Git.

Первую копию проверьте вручную:

```sh
sudo -u movie-helper-deploy python3 /opt/movie-helper/backup-tools/scheduled_backup.py
```

После успешного запуска установите `deploy/movie-helper-backup.cron` в
`/etc/cron.d/movie-helper-backup` (root:root, 0644), а
`deploy/movie-helper-backup.logrotate` в `/etc/logrotate.d/movie-helper-backup`.
Расписание предполагает UTC на сервере: ежедневно 01:00 UTC / 04:00 МСК.
Лог: `/opt/movie-helper/backup.log`; время последнего полностью успешного запуска:
`/opt/movie-helper/backup-last-success.json`. Уведомления в Telegram не настроены.

После успешного скачивания и проверки новой копии сохраняются последние 30
регулярных архивов. Удаление в B2 окончательное, чтобы скрытые версии не занимали
квоту; обработка ограничена именами `daily-<UTC>-<id>.tar.gz` внутри `archives`.
Не загруженные из-за ошибок локальные снимки сохраняются, поэтому при длительном
сбое требуется контроль диска. Отдельные старые копии перед деплоем в
`/opt/movie-helper/backups/` этот скрипт не переносит и не удаляет.

Для восстановления используйте тот же пароль crypt и remote `backup:` (при
потере сервера B2 application key можно перевыпустить), выберите архив:

```sh
sudo -u movie-helper-deploy rclone --config /opt/movie-helper/secrets/rclone.conf lsf backup:
```

Скачайте выбранное имя через `rclone copyto backup:<имя> <локальный-путь>` с тем
же `--config`, проверьте архив, остановите бота и восстановите его в **новый пустой
volume** с владельцем 65532:65532 согласно процедуре выше. На проверочной копии
бот не запускается: это исключает повторные отправки в Telegram.

## Деплой через GitHub Actions

На сервере нужны Docker, Compose **2.30+** (поддержка raw env_file), Python 3 и отдельный SSH-пользователь с доступом к Docker и каталогу `/opt/movie-helper/releases`. Не запускайте вторую копию бота с тем же токеном. Вход CI использует отдельный ключ, проверенный host key и отключённые SSH forwarding/PTY. Участник группы `docker` фактически имеет административный доступ к серверу.

В Repository Actions Secrets: `BOT_TOKEN`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `TMDB_API_TOKEN`, `DEPLOY_SSH_KEY` (полный приватный ключ). В Actions Variables: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` (проверенная строка known_hosts); необязательно `DEPLOY_PORT` (по умолчанию 22), `ALLOWED_CHAT_IDS` и `AI_RESULT_MODE` (`warmup` по умолчанию, затем `background` после заполнения пулов).

В **Actions → Check and build → Run workflow** выберите `main`, включите `deploy`. Поле `allowed_chat_ids` принимает ID групп через запятую или `bootstrap`. Пустое поле использует Actions Variable `ALLOWED_CHAT_IDS`, а при её отсутствии сохраняет предыдущее значение на сервере. При самом первом запуске это **bootstrap**: доступны `/id` и справка в личке, группы и расписания заблокированы. После получения ID тестовой группы повторите запуск с этим ID. Рубрики включаются отдельно командами участников.

Deployment job использует environment `production` и запускается после успешных проверок и публикации при каждом push в `main` либо вручную с включённым `deploy`. Деплои сериализованы: текущий деплой не прерывается следующим. Настройки чатов, расписания и данные сохраняются на сервере; пустой `allowed_chat_ids` использует Actions Variable `ALLOWED_CHAT_IDS` либо прежнее значение.

Скрипт передаёт секреты по SSH через stdin, хранит runtime.env в закрытом каталоге релиза с правами 0600 и загружает образ **по digest**, полученному от publish-job. Для чтения GHCR временно используется job-scoped `GITHUB_TOKEN`; Docker login сервера хранится только во временном каталоге на время pull. Секреты не включаются в образ. Значения с `$` и кавычками сохраняются через raw env_file; переводы строк в значениях запрещены.

Файлы релизов лежат в `/opt/movie-helper/releases/`, активный релиз — symlink `/opt/movie-helper/current`; Compose project — `movie-helper`, постоянный volume — `movie-helper-data`. Это отдельный volume от обычного локального `docker compose up` из корня репозитория. Деплой не переносит существующую БД из другого проекта автоматически.

Новый образ загружается до остановки старого бота. После остановки создаётся согласованный архив `/data` в `/opt/movie-helper/backups/<release>.tar.gz`; затем запускается новый контейнер. Проверяются отсутствие рестартов и сообщение об успешной инициализации. Это ещё не проверка отправки Telegram-сообщения или ответа Gemini. Архивы и старые релизы автоматически не удаляются: перенесите резервные копии во внешнее хранилище и контролируйте место.

При ошибке до обновления БД старый бот сохраняется либо запускается обратно после неудачного бэкапа. Если новый контейнер не проходит проверку запуска, он останавливается, а старый образ **не запускается автоматически** на потенциально изменённой схеме. Для отката остановите бота, восстановите соответствующий архив в пустой volume с владельцем 65532:65532 и используйте предыдущий релиз из `previous.txt`. Не распаковывайте архив поверх работающей SQLite.

Операционные команды на сервере:

```sh
cd /opt/movie-helper/current
docker compose --env-file image.env -f compose.yaml ps
docker compose --env-file image.env -f compose.yaml logs --tail=100 bot
```

## Разработка

```sh
go test -race ./...
go vet ./...
docker build -t movie-helper:local .
```

Для `go run ./cmd/bot` переменные окружения задаются в оболочке; `.env` читается Docker Compose, само приложение файл не загружает. Локальная БД по умолчанию `data/movie-helper.db`, путь меняется через `DB_PATH`. Целевая ОС — Linux (файловая блокировка `flock`).

Пакеты: `config` — конфигурация; `telegram` — команды и доставка; `daily` — ежедневные рубрики; `clubprofile` — анонимные киноопросы, просмотры и профиль клуба; `featurevote` — сбор идей и голосование; `storage` — SQL и миграции; `scheduler` — расписание; `aiwork` — долговечная фоновая очередь; `content` — выбор источника и пополнение пулов; `ai` — общие промпты и проверка результата; `meme`, `gemini` и `groq` — внешние адаптеры. Сборка зависимостей в `cmd/bot`.

Тесты используют реальные временные SQLite и подменённые HTTP/Telegram, проверяют изоляцию, права, повторы, перезапуск, DST, ошибки доставки, источники и предел Gemini. Для проверки настоящей интеграции нужны отдельный Telegram-токен, тестовая группа и Gemini-ключ: проверить `/id`, команды управления от обычного участника, фото по `file_id`, обе рубрики и сохранение очереди после пересоздания контейнера.

### Проверка мемов без публикации

`go run ./cmd/check-memes -provider groq -state /tmp/movie-helper-meme-check` запускает тот же отбор с настоящими источниками и ключом из окружения и выводит до трёх одобренных кандидатов. Для Gemini задайте `-provider gemini`. Команда не подключается к Telegram и использует отдельную диагностическую SQLite; не указывайте каталог данных бота. Внешняя квота API расходуется, счётчики работающего бота не меняются. Предел диагностики — 6 запросов на провайдера за UTC-сутки.

В каталоге сохраняются `candidates.json` для повторяемой проверки и кэш отклонений. Повторный запуск пропускает отклонённые картинки и берёт следующие из той же подборки; после успешного выбора повторный запуск может выбрать её снова. Для новой подборки удалите только `candidates.json`. Между проверками Groq выдерживайте минимум минуту, чтобы уменьшить вероятность `429`. Логи показывают размеры подготовленных картинок, размер запроса, HTTP-статус, время ответа и причины решений.

## Напоминания между киноклубами

Любой участник разрешённой группы задаёт ежемесячную встречу и время напоминаний:

```text
/timezone Europe/Moscow
/club_schedule fri 2 19:00
/club_settings
/club_preview
/club_pause
```

`fri 2` — вторая пятница каждого месяца; доступны `mon..sun`, `1..4` и `last`
(последний выбранный день месяца). Время относится к напоминаниям. Они приходят
через 10 и 17 календарных дней после расчётной встречи. Например, после 9 октября
2026 года — 19 и 26 октября, до следующей второй пятницы 13 ноября. Реальное
проведение встречи бот не отслеживает. Перенос отдельной встречи пока требует
паузы или изменения постоянного правила.

Функция изначально выключена. Настройка/preview доступны всем участникам;
`/club_settings` доступна участникам. Смена расписания или timezone отменяет
неотправленные старые слоты. Старые сообщения после включения не догоняются;
после простоя отправка допустима в течение шести часов от слота.

Gemini с резервом Groq готовит в фоне пять текстов на чат: три приглашения
поискать варианты и два вернуться к обсуждению. Генерация имеет низкий приоритет,
использует общие квоты AI и не передаёт переписку участников. После трёх последовательных отсрочек Gemini по Retry-After следующее фоновое обращение использует Groq; он пополняет текущий запас, а следующий цикл пополнения снова начинается с Gemini. Счётчик сохраняется в БД. Тон случайный:
дружеский, театральный, саркастичный, матерный или roast клуба в целом.
Ориентир 100–180 слов, допустимо 60–240, до 2200 символов. Локальная проверка
отбрасывает разметку, упоминания и слишком похожие тексты; она не гарантирует
семантическое качество. Не используются конкретные имена участников или фильмы.

Отправка и preview читают готовый запас; при пустом запасе используются локальные
шаблоны. `/club_preview` не расходует текст. `/club_settings` показывает запас и
ошибки доставки. AI недоступность не создаёт сообщения об ошибке в группе.
Постеров, подборок, автоматических голосований и отдельного уведомления о
пополнении нет. Текст закрепляется за доставкой до сети и не меняется при retry. Уже отправленное или неопределённое напоминание того же цикла не создаётся повторно при смене расписания или часового пояса. Retry-After отсчитывается после получения ответа провайдера или Telegram.

После неоднозначной доставки или restart во время отправки проверьте чат и
выполните `/club_resolve ID sent|retry|cancel`. Автоматически повторяется только
явный Telegram 429, по Retry-After и в пределах окна. Утрата доступа отключает
напоминания. `/resume` сам их не включает: повторите `/club_schedule`.


## Линтеры и архитектурные границы

В `.golangci.yml` явно включены 48 линтеров, версия в CI закреплена: **v2.14.0**, сборка с Go **1.27.1**. Команды для того же инструмента локально:

```sh
GOBIN="$PWD/.tools" GOTOOLCHAIN=go1.27.1 go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.14.0
.tools/golangci-lint config verify
.tools/golangci-lint run ./...
python3 scripts/check_lint_guards.py --linter "$PWD/.tools/golangci-lint"
```

Основные группы защиты:

- `depguard`: доменные пакеты используют порты, не SQL/HTTP/конкретные адаптеры; Telegram не импортирует storage/AI/TMDB; storage не вызывает внешние адаптеры.
- `interfacebloat`, `iface`, `gocognit`: до семи объявленных методов на порт, когнитивная сложность production-функции до 15. Старые функции не исключены. Составные интерфейсы нужны для сборки зависимостей; внутри сервисов и координаторов используются отдельные узкие порты. Проверка interfacebloat не считает развёрнутые методы вложенных интерфейсов.
- `contextcheck`, `containedctx`, `fatcontext`, `noctx`, `forbidigo`: контекст наследуется от вызывающего кода; блокирующий `time.Sleep` запрещён в production, непосредственный `time.Now` запрещён в чистой политике напоминаний и её хранилище.
- `errorlint`, `errname`, `forcetypeassert`, `nilnesserr`, `exhaustive`: корректная работа с обёрнутыми ошибками, безопасные assertions, обработка всех известных enum-состояний. Exhaustive защищает типизированные enum; строки состояний требуют тестов переходов.
- `govet`, `staticcheck`, `gocritic`, `durationcheck`, `gosec`, `bidichk`: подозрительные конструкции, ошибочная арифметика длительностей, безопасность и скрытые символы.
- `bodyclose`, `sqlclosecheck`, `rowserrcheck`, `errcheck`: HTTP/SQL-ресурсы и ошибки. `loggercheck`, `sloglint` проверяют структурированные логи.

Для тестов оставлены отдельные правила: проверки сложности, повторяющихся литералов, закрытия fixture-ресурсов и создания корневого контекста не применяются как к production. При этом assertions, enum-переключения и SQL-вызовы с контекстом проверяются и в тестах. Любой `nolint` требует конкретного имени линтера и объяснения; общих исключений для старых функций или интерфейсов нет.

`check_lint_guards.py` проверяет правила на плохом и корректном примерах в отдельном временном модуле. Эта проверка запускается и в CI. Линтеры не доказывают правильность календаря, Retry-After, идемпотентности доставки или миграций SQLite — эти свойства защищают регрессионные тесты и `go test -race ./...`.
