# Movie Helper

Telegram-бот для дружеского киноклуба: **мем дня, факт о кино и опросы по жанрам с подборкой фильмов**. Для ежедневных рубрик используется автоматический отбор Gemini с резервом Groq; подборки фильмов строятся по данным TMDB без LLM.

Go 1.27.1, `go-telegram/bot`, SQLite с миграциями Goose, один процесс long polling. Docker Compose хранит данные в volume; домен и входящие порты не нужны.

## Запуск

1. Создайте бота через [BotFather](https://t.me/BotFather), добавьте в группу и разрешите отправлять текст, фотографии и опросы. Выдавать административные права самому боту не требуется. Команды адресуйте `/help@имя_бота`, особенно при включённом Privacy Mode. `/help` показывает основные команды, `/help_admin` — справку по модерации и восстановлению после сбоев. Справка доступна всем; права на выполнение команд не меняются.
2. Подготовьте конфигурацию:

   ```sh
   cp .env.example .env
   chmod 600 .env
   ```

   В `.env` заполните `BOT_TOKEN`, `ALLOWED_CHAT_IDS` (отрицательные ID групп через запятую), `TMDB_API_TOKEN` для киноопросов и хотя бы один AI-ключ для мемов и фактов. Используется TMDB API Read Access Token (Bearer), а не короткий API key. Реальные ключи не добавляйте в Git. Для первого определения ID задайте `ALLOWED_CHAT_IDS=bootstrap` (ни одна группа пока не разрешена), запустите бота и отправьте `/id@имя_бота` в нужной группе: эта команда работает вне списка. Затем обновите `.env` и пересоздайте контейнер.
3. Запустите:

   ```sh
   docker compose up -d --build
   docker compose logs --tail=100 -f bot
   ```

4. Администратор группы явно включает рубрики:

   ```text
   /timezone@имя_бота Europe/Moscow
   /schedule@имя_бота meme 09:00
   /schedule@имя_бота fact 12:00
   /settings@имя_бота
   ```

Рассылка изначально выключена. Время относится к часовому поясу чата. Если сегодняшнее время уже наступило, первое сообщение будет завтра. `/pause meme` и `/pause fact` выключают соответствующую рубрику. Изменения `.env` применяются через `docker compose up -d --force-recreate`, а не `restart`.

Один токен обслуживает один процесс. Активный webhook препятствует запуску; приложение не удаляет его автоматически. Второй процесс с той же БД блокируется файловой блокировкой. SQLite рассчитана на локальный Docker volume одного сервера.

## Киноопросы и подборки

Функция изначально выключена. Администратор может запустить короткий тест или добавить отдельный еженедельный слот на любой день, вплоть до семи дней в неделю:

```text
/genre_poll@имя_бота 5m
/movie_schedule@имя_бота genre wed 19:00
/movie_schedule@имя_бота genre sat 18:00
/movie_settings@имя_бота
/movie_pause@имя_бота genre wed
/movie_pause@имя_бота genre
```

Без длительности `/genre_poll` работает 24 часа; для быстрой проверки укажите `5m` или `10m`. Допустимый диапазон — от 5 минут до 24 часов. Плановый опрос тоже длится 24 часа. Он анонимный, содержит 10 ротируемых жанров и позволяет изменить голос. Бот сохраняет только итоговые счётчики, без Telegram ID голосовавших.

После закрытия бот получает через TMDB до 20 популярных фильмов с русскими названиями и описаниями. Первые 10 публикуются сразу вместе с постерами, следующие — один раз по кнопке «Ещё 10». Недавно показанные в этом чате фильмы исключаются на 90 дней. При недоступности TMDB фильмы не выдумываются и AI-квота не расходуется. Одновременно в чате может идти один киноопрос.

Если отправка завершилась неоднозначно, `/movie_settings` покажет раунд. После проверки чата администратор выполняет `/movie_resolve ID sent`, `/movie_resolve ID retry` или `/movie_resolve ID cancel`. `/about` показывает участникам источник данных и правила приватности.

Названия, описания, рейтинги и изображения предоставлены [TMDB](https://www.themoviedb.org/). This product uses the TMDB API but is not endorsed or certified by TMDB. У TMDB нет обещанного SLA; условия и разрешённое использование нужно периодически перепроверять.

## Откуда берутся материалы

**По умолчанию материалы отбирает и одобряет AI; участие человека не требуется.** Предложения участников сохраняются, но в автоматическом режиме не публикуются. Источники:

- Мемы: [Meme API](https://github.com/D3vd/Meme_Api), по умолчанию `RUSSIANMemeSub,Pikabu,expectedrussians`. Бот запрашивает до 50 записей на каждый subreddit; провайдер может вернуть меньше. Действуют фильтры NSFW/спойлеров, русскоязычного заголовка и формата JPG/PNG с `i.redd.it`. Для AI используется самый крупный безопасный `preview.redd.it`, а в Telegram публикуется оригинал. При отсутствии preview разрешён оригинал до 8 MiB; перед AI изображение проверяется по размерности и уменьшается до 1280 px (JPEG quality 85, маленький PNG сохраняется, если он компактнее). Gemini просматривает до четырёх картинок за запрос, резервный Groq — одну; максимум две порции на провайдера. Модель отмечает все подходящие варианты и выбирает лучший: первый резервируется для текущей доставки, до двух дополнительных сохраняются в chat-scoped AI-очереди на следующие дни. Содержательные и постоянные технические отказы кэшируются в SQLite на 24 часа; история публикаций отдельная для каждого чата. `MEME_SUBREDDITS` позволяет задать до пяти источников через запятую.
- Факты: разделы Production/Development/Filming английской Wikipedia через [MediaWiki TextExtracts](https://www.mediawiki.org/wiki/Extension:TextExtracts). AI готовит до 40 слов по-русски и возвращает подтверждающую цитату, наличие которой проверяет код. Ссылка берётся из ответа Wikipedia, привязана к редакции статьи; добавлены атрибуция, отметка переработки и [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). Такая проверка уменьшает выдумки, но не доказывает истинность текста модели или самой статьи.

Стартовый список содержит 20 фильмов. На одну попытку получения факта читается до трёх ещё не использованных статей. Для каждого чата список перемешивается; предпросмотры и повторные попытки берут следующую порцию без повторения статей до конца круга, затем оставшиеся доступные фильмы перемешиваются заново. Этот порядок хранится в памяти и сбрасывается при перезапуске; история публикаций сохраняется в SQLite. **Один автоматический факт на название статьи в каждом чате.** При исчерпании списка пополните `FACT_WIKI_TITLES` английскими заголовками статей, разделёнными `|` (до 100), например:

```dotenv
FACT_WIKI_TITLES='Alien (film)|The Matrix|Jurassic Park (film)'
```

Это начальный ограниченный каталог, а не бесконечный поиск по интернету. Пустой `FACT_WIKI_TITLES` включает встроенный список. Статьи без подходящего раздела пропускаются. Переписка участников, их имена и ручная очередь провайдерам AI не передаются: только общедоступные картинки, заголовки и фрагменты статей.

Без обоих ключей (`GEMINI_API_KEY` и `GROQ_API_KEY`) автоматические рубрики и предпросмотр не получают материалов; доступна ручная очередь при `/moderation on`. При ошибке или исчерпании лимита Gemini бот пробует Groq, если он настроен. Валидный полный отказ Gemini не обходится резервной моделью. Перед обращением к источнику планировщик использует ранее одобренный запас этого чата. Если подходящего материала и запаса нет либо источник/AI недоступен, планировщик делает первую попытку и до пяти повторов с паузами 5, 15, 30, 60 и 120 минут. После шести неудач, исчерпания окна или недоступности квоты материал может не выйти; непроверенный контент не публикуется. `/settings` показывает последнюю безопасную причину подготовки. Предпросмотр не создаёт отложенных повторов и не пополняет запас.

### Режим публикации и быстрая проверка

Настройка отдельная для каждого чата и хранится в SQLite:

- `/moderation off` — по умолчанию: AI выбирает материалы, они публикуются по расписанию без ручного одобрения. Сохранённые результаты AI после отмены или явного `/resolve ID requeue` также могут использоваться; ручные предложения не публикуются.
- `/moderation on` — публикуются только материалы после `/approve ID` администратором. Если одобренных нет, AI подбирает материал в очередной слот и сохраняет его в `/queue` со статусом `pending`; публикация возможна в следующий слот после одобрения. В этом режиме можно публиковать и предложения участников.
- `/settings` показывает режим и расписание. Переключение режима сохраняет материалы и отменяет ожидающие доставки; сетевой запрос, уже отправленный в Telegram, может завершиться. Расписание при переключении не включается автоматически.

Для немедленной проверки администратор отправляет в разрешённую группу:

```text
/preview@имя_бота meme
/preview@имя_бота fact
```

Бот пришлёт пробный материал с пометкой «Предпросмотр». Команды используют те же источники, AI и дневные лимиты провайдеров, но не включают расписание, не пополняют очередь и не отмечают материал как опубликованный. Поэтому он может встретиться позже в ежедневной рубрике. Отказ модели, недоступность источников и лимит обрабатываются без публикации непроверенных материалов.

Существующие чаты после обновления тоже получают `/moderation off`; прежние ручные предложения остаются в базе. Для их публикации включите `/moderation on`.

### Gemini и Groq

Ключ создаётся в [Google AI Studio](https://aistudio.google.com/apikey). Модель задаётся `GEMINI_MODEL`, по умолчанию `gemini-3.8-flash`; используется REST `generateContent` со структурированным JSON-ответом. Выбранная замена должна поддерживать изображения и JSON Schema.

`GEMINI_DAILY_REQUEST_LIMIT=20` — общий предел **попыток** обращения ко всем чатам за UTC-сутки. Счётчик хранится в SQLite и переживает перезапуск; ошибки тоже расходуют попытку. `0` блокирует вызовы модели. Успешный подбор двух рубрик требует минимум двух вызовов; отказы, повторы и предпросмотры расходуют дополнительные попытки. Это ограничение числа запросов, а не бюджета в деньгах: проверьте [тариф модели](https://ai.google.dev/gemini-api/docs/pricing), [квоты проекта](https://ai.google.dev/gemini-api/docs/rate-limits), [доступность региона](https://ai.google.dev/gemini-api/docs/available-regions) и [условия обработки данных](https://ai.google.dev/gemini-api/terms).

Встроенный Google Search grounding не используется. Независимые источники позволяют сохранять очередь и публиковать её по расписанию без привязки к поисковому ответу конкретному пользователю.

Groq — отдельный резервный провайдер: `GROQ_API_KEY`, модель `GROQ_MODEL=qwen/qwen3.8-27b`, сохраняемый предел `GROQ_DAILY_REQUEST_LIMIT=20` попыток за UTC-сутки. Его счётчик независим от Gemini; `0` отключает вызовы Groq. Если задан только Groq-ключ, бот работает через него. При двух ключах порядок Gemini → Groq; для факта — один вызов и максимум одна дополнительная попытка исправить длину ответа, индекс статьи или недословную цитату с повторной проверкой по источнику; для мемов — до двух вызовов с разными кандидатами. Каждая попытка отдельно расходует дневной лимит, включая ошибки. Один HTTP-запрос к Gemini может ждать до 60 секунд, к Groq — до 25 секунд. На подбор у Gemini (картинки и до двух запросов) выделено 150 секунд, у Groq — 60 секунд. Общий предел получения материала — 4 минуты, команда предпросмотра имеет ещё 30 секунд для проверки прав и ответа в Telegram. Обычные команды сохраняют тайм-аут 25 секунд. Поэтому при медленном Gemini предпросмотр может занять несколько минут; явные ошибки HTTP сразу передают управление резерву. Ошибки HTTP, тайм-аут и непрошедший проверку ответ позволяют перейти к резерву. В логах сохраняются безопасные коды ошибок HTTP и проверки ответа; ключи и полные ответы с ошибками не попадают в логи.

Для Groq используются строгая JSON Schema, `reasoning_effort=none` и до 512 выходных токенов. Для мемов берётся одна картинка за запрос, чтобы оставить запас для следующего кандидата в бесплатном лимите 8000 токенов/минуту. Сжатие уменьшает байты запроса, но не фиксированную стоимость изображения в токенах Groq. Разные запросы всё равно могут суммарно достичь лимита: после `429` повторите позже. Для фактов проверяется дословная непрерывная цитата из источника: целевая длина 5–20 слов, допустимо до 40 слов и 400 символов (минимум 20 символов); сам факт — до 40 слов. При нарушении бот один раз просит AI исправить ответ, учитывая общий дневной лимит; ограничения не ослабляются при переключении. Модель Groq находится в Preview, доступность и квоты могут меняться: [vision](https://console.groq.com/docs/vision), [лимиты](https://console.groq.com/docs/rate-limits), [данные](https://console.groq.com/docs/your-data).

## Очередь и права

- Участник отвечает `/suggest_meme@имя_бота` на одну фотографию, не альбом. Бот сохраняет Telegram `file_id`, без скачивания файла. С Privacy Mode надёжнее адресовать команду явно.
- `/suggest_fact Текст факта | https://источник` добавляет предложение с текстом до 1500 символов.
- Администратор открывает `/queue`, затем `/review ID` и нажимает «Одобрить» или «Убрать». Есть команды `/approve ID` и `/reject ID`. Для следующей страницы: `/queue последний_ID`.
- Ручное предложение публикуется только после одобрения. Автоматически отобранные внешние материалы публикуются без отдельного одобрения.
- Изменять расписание и очередь могут владельцы и администраторы текущей группы, проверяемые через Telegram. Анонимные команды от имени чата не принимаются. При ошибке проверки права не предоставляются.
- Материалы, история повторов и настройки изолированы по `chat_id`; ID материала чужого чата не даёт к нему доступ. Эти данные доступны участникам своей группы и оператору сервера, а не являются зашифрованным хранилищем.

## Доставка и восстановление

Проверка расписания идёт каждые 15 секунд. Один слот каждой рубрики на локальную дату; окно подбора и отправки — до 6 часов после назначенного времени, но не позже конца местного дня. После простоя публикация догоняется только внутри этого окна. Число попыток и время следующего подбора хранятся в SQLite и сохраняются при перезапуске; прерванный подбор повторяется не раньше чем через 5 минут после запуска. При смене режима, времени или часового пояса ожидающие доставки отменяются, материал возвращается в очередь. Уже отправляемый сетевой запрос может завершиться.

После подтверждённого Telegram `429` учитывается `retry_after` в пределах окна. При потере доступа к чату рассылка выключается: восстановите права, выполните `/resume` и снова `/schedule`. Преобразование группы в supergroup требует нового `ALLOWED_CHAT_IDS` и настройки в новом чате; старая история сохраняется под старым ID и автоматически не переносится.

Telegram и SQLite не имеют общей транзакции. После таймаута или падения между отправкой и записью результата доставка становится `unknown` и автоматически не повторяется. `/settings` показывает ожидающие повторы, число попыток, время следующего подбора, а также последние пропущенные, неопределённые и ошибочные доставки. Проверьте чат и выполните `/resolve ID sent`, если пост появился, либо `/resolve ID requeue`, чтобы вернуть материал в очередь **следующего доступного дня**. Во втором случае возможен повтор. Материал публикуется в подходящем режиме: ручное предложение требует `/moderation on`, результат Gemini — его AI-одобрения в автоматическом режиме или одобрения администратора в ручном. Строгая exactly-once доставка не обещается.

Логи содержат тип события и технические ID, без токенов, текста переписки и полных ответов внешних API. Для публичных мемов дополнительно записываются размеры копий, ссылка-идентификатор источника и проверенная краткая причина решения AI. Недоступность источника видна в логах. Ошибочные материалы не повторяются бесконечно.

## Обновление, CI и резервные копии

Workflow проверяет форматирование, `go vet`, тесты с race, `golangci-lint`, Compose и Docker build. Локально линтер запускается командой `golangci-lint run ./...`; для Go 1.27 нужна версия не ниже 2.13.0, в CI зафиксирована 2.13.2. После успешных проверок push в `main` или тега `v*` публикует `ghcr.io/vaporon4a/movie-helper:sha-<полный commit SHA>`. Push в `main` затем автоматически обновляет сервер опубликованным образом этого коммита. PR образ не публикует, теги сервер не обновляют. Публикация требует разрешения GitHub Packages для репозитория. Для приватного GHCR серверу нужен отдельный вход с правом чтения пакета.

Для готового образа задайте `BOT_IMAGE` в `.env`, затем:

```sh
docker compose pull bot
docker compose up -d --no-build
```

Перед обновлениями сохраняйте volume с остановленным ботом. Пример согласованной копии (архив включает БД и возможные WAL-файлы):

```sh
docker compose stop bot
mkdir -p backups
bot_volume=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps -aq bot)")
bot_backup="movie-helper-$(date -u +%Y%m%dT%H%M%SZ).tgz"
docker run --rm --mount "source=$bot_volume,target=/data,readonly" \
  --mount "type=bind,src=$PWD/backups,target=/backup" alpine:3.23 \
  tar czf "/backup/$bot_backup" -C /data .
docker compose start bot
```

Скопируйте архив во внешнее место; `.env` храните отдельно. Для восстановления остановите бота, распакуйте архив в **новый пустой volume**, сохраните владельца `65532:65532` и подключите его вместо `bot-data`. Проверьте `/settings` и `/queue`, прежде чем включать рассылку. Не копируйте отдельный файл работающей SQLite и не используйте `docker compose down -v`: он удаляет данные. Откат приложения с несовместимой схемой требует совместимой резервной копии; автоматического Down при запуске нет.

### Ежедневные копии в Backblaze B2

`deploy/scheduled_backup.py` останавливает работающего бота, архивирует `/data`,
запускает тот же контейнер и затем проверяет SQLite, загружает архив через
`rclone crypt`, скачивает его обратно и сверяет SHA-256. Общая блокировка с деплоем
исключает обновление во время снимка. При ошибке архивации выполняется попытка
запуска бота; SIGKILL или отключение сервера требуют отдельной проверки состояния.
Если бот уже остановлен, скрипт завершится с ошибкой, не включая его самостоятельно.

Конфигурация для production: закрытый bucket `movie-helper-backups-20260923`,
подкаталог `archives`, конфиг `/opt/movie-helper/secrets/rclone.conf` (0600),
пользователь `movie-helper-deploy`. На сервере нужны Python 3, Docker и rclone.
Скопируйте `remote.py`, `configure_backup.py` и `scheduled_backup.py` из `deploy/`
в `/opt/movie-helper/backup-tools/`; эти инструменты устанавливаются отдельно от
релизов и не обновляются автоматически вместе с ботом.

Для ввода ключа запустите **в собственном интерактивном SSH-терминале**:

```sh
sudo -u movie-helper-deploy python3 /opt/movie-helper/backup-tools/configure_backup.py
```

Скрипт запросит keyID, applicationKey и пароль шифрования (от 24 символов) с
повтором. Ввод скрыт, существующий конфиг не перезаписывается. Ключ B2 должен
иметь доступ к этому bucket на просмотр, чтение, запись и удаление файлов.
Пароль шифрования заранее сохраните в менеджере паролей вне сервера: без него
восстановить архивы невозможно. Обфускация пароля в rclone.conf обратима, поэтому
весь конфиг является секретом; не выводите его в логи и не добавляйте в Git.

Первую копию проверьте вручную:

```sh
sudo -u movie-helper-deploy python3 /opt/movie-helper/backup-tools/scheduled_backup.py
```

После успешного запуска установите `deploy/movie-helper-backup.cron` в
`/etc/cron.d/movie-helper-backup` (root:root, 0644), а
`deploy/movie-helper-backup.logrotate` в `/etc/logrotate.d/movie-helper-backup`.
Расписание предполагает UTC на сервере: ежедневно 01:00 UTC / 04:00 МСК.
Лог: `/opt/movie-helper/backup.log`; время последнего полностью успешного запуска:
`/opt/movie-helper/backup-last-success.json`. Уведомления в Telegram не настроены.

После успешного скачивания и проверки новой копии сохраняются последние 30
регулярных архивов. Удаление в B2 окончательное, чтобы скрытые версии не занимали
квоту; обработка ограничена именами `daily-<UTC>-<id>.tar.gz` внутри `archives`.
Не загруженные из-за ошибок локальные снимки сохраняются, поэтому при длительном
сбое требуется контроль диска. Отдельные старые копии перед деплоем в
`/opt/movie-helper/backups/` этот скрипт не переносит и не удаляет.

Для восстановления используйте тот же пароль crypt и remote `backup:` (при
потере сервера B2 application key можно перевыпустить), выберите архив:

```sh
sudo -u movie-helper-deploy rclone --config /opt/movie-helper/secrets/rclone.conf lsf backup:
```

Скачайте выбранное имя через `rclone copyto backup:<имя> <локальный-путь>` с тем
же `--config`, проверьте архив, остановите бота и восстановите его в **новый пустой
volume** с владельцем 65532:65532 согласно процедуре выше. На проверочной копии
бот не запускается: это исключает повторные отправки в Telegram.

## Деплой через GitHub Actions

На сервере нужны Docker, Compose **2.30+** (поддержка raw env_file), Python 3 и отдельный SSH-пользователь с доступом к Docker и каталогу `/opt/movie-helper/releases`. Не запускайте вторую копию бота с тем же токеном. Вход CI использует отдельный ключ, проверенный host key и отключённые SSH forwarding/PTY. Участник группы `docker` фактически имеет административный доступ к серверу.

В Repository Actions Secrets: `BOT_TOKEN`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `TMDB_API_TOKEN`, `DEPLOY_SSH_KEY` (полный приватный ключ). В Actions Variables: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` (проверенная строка known_hosts); необязательно `DEPLOY_PORT` (по умолчанию 22), `ALLOWED_CHAT_IDS`.

В **Actions → Check and build → Run workflow** выберите `main`, включите `deploy`. Поле `allowed_chat_ids` принимает ID групп через запятую или `bootstrap`. Пустое поле использует Actions Variable `ALLOWED_CHAT_IDS`, а при её отсутствии сохраняет предыдущее значение на сервере. При самом первом запуске это **bootstrap**: доступны `/id` и справка в личке, группы и расписания заблокированы. После получения ID тестовой группы повторите запуск с этим ID. Рубрики включаются отдельно командами администратора.

Deployment job использует environment `production` и запускается после успешных проверок и публикации при каждом push в `main` либо вручную с включённым `deploy`. Деплои сериализованы: текущий деплой не прерывается следующим. Настройки чатов, расписания и данные сохраняются на сервере; пустой `allowed_chat_ids` использует Actions Variable `ALLOWED_CHAT_IDS` либо прежнее значение.

Скрипт передаёт секреты по SSH через stdin, хранит runtime.env в закрытом каталоге релиза с правами 0600 и загружает образ **по digest**, полученному от publish-job. Для чтения GHCR временно используется job-scoped `GITHUB_TOKEN`; Docker login сервера хранится только во временном каталоге на время pull. Секреты не включаются в образ. Значения с `$` и кавычками сохраняются через raw env_file; переводы строк в значениях запрещены.

Файлы релизов лежат в `/opt/movie-helper/releases/`, активный релиз — symlink `/opt/movie-helper/current`; Compose project — `movie-helper`, постоянный volume — `movie-helper-data`. Это отдельный volume от обычного локального `docker compose up` из корня репозитория. Деплой не переносит существующую БД из другого проекта автоматически.

Новый образ загружается до остановки старого бота. После остановки создаётся согласованный архив `/data` в `/opt/movie-helper/backups/<release>.tar.gz`; затем запускается новый контейнер. Проверяются отсутствие рестартов и сообщение об успешной инициализации. Это ещё не проверка отправки Telegram-сообщения или ответа Gemini. Архивы и старые релизы автоматически не удаляются: перенесите резервные копии во внешнее хранилище и контролируйте место.

При ошибке до обновления БД старый бот сохраняется либо запускается обратно после неудачного бэкапа. Если новый контейнер не проходит проверку запуска, он останавливается, а старый образ **не запускается автоматически** на потенциально изменённой схеме. Для отката остановите бота, восстановите соответствующий архив в пустой volume с владельцем 65532:65532 и используйте предыдущий релиз из `previous.txt`. Не распаковывайте архив поверх работающей SQLite.

Операционные команды на сервере:

```sh
cd /opt/movie-helper/current
docker compose --env-file image.env -f compose.yaml ps
docker compose --env-file image.env -f compose.yaml logs --tail=100 bot
```

## Разработка

```sh
go test -race ./...
go vet ./...
docker build -t movie-helper:local .
```

Для `go run ./cmd/bot` переменные окружения задаются в оболочке; `.env` читается Docker Compose, само приложение файл не загружает. Локальная БД по умолчанию `data/movie-helper.db`, путь меняется через `DB_PATH`. Целевая ОС — Linux (файловая блокировка `flock`).

Пакеты: `config` — конфигурация; `telegram` — команды и доставка; `daily` — общие типы; `storage` — SQL и миграции; `scheduler` — расписание; `content` — выбор источника; `ai` — общие промпты и проверка результата; `meme`, `gemini` и `groq` — внешние адаптеры. Сборка зависимостей в `cmd/bot`. Будущие фильмы, встречи, опросы и рейтинг можно добавлять отдельными пакетами и миграциями.

Тесты используют реальные временные SQLite и подменённые HTTP/Telegram, проверяют изоляцию, права, повторы, перезапуск, DST, ошибки доставки, источники и предел Gemini. Для проверки настоящей интеграции нужны отдельный Telegram-токен, тестовая группа и Gemini-ключ: проверить `/id`, административные команды, фото по `file_id`, обе рубрики и сохранение очереди после пересоздания контейнера.

### Проверка мемов без публикации

`go run ./cmd/check-memes -provider groq -state /tmp/movie-helper-meme-check` запускает тот же отбор с настоящими источниками и ключом из окружения и выводит до трёх одобренных кандидатов. Для Gemini задайте `-provider gemini`. Команда не подключается к Telegram и использует отдельную диагностическую SQLite; не указывайте каталог данных бота. Внешняя квота API расходуется, счётчики работающего бота не меняются. Предел диагностики — 6 запросов на провайдера за UTC-сутки.

В каталоге сохраняются `candidates.json` для повторяемой проверки и кэш отклонений. Повторный запуск пропускает отклонённые картинки и берёт следующие из той же подборки; после успешного выбора повторный запуск может выбрать её снова. Для новой подборки удалите только `candidates.json`. Между проверками Groq выдерживайте минимум минуту, чтобы уменьшить вероятность `429`. Логи показывают размеры подготовленных картинок, размер запроса, HTTP-статус, время ответа и причины решений.
